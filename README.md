# Riverbend work orders

A small service that turns messy inbound customer messages into structured, priced work orders
for a fictional three-shop bicycle repair chain. Each shop is a tenant and never sees another
shop's data. Built for a take-home brief; the brief's deliverables map to:

## Run it

Prerequisites: Docker. Copy `.env.example` to `.env`. With `LLM_PROVIDER=fake` (the default) no
model key is needed; the pipeline runs on a stand-in provider.

```
make run        # Postgres (host :5433) + Pub/Sub emulator + migrate/seed + API :8080 + worker :8081
make samples    # send the 40 sample messages, reply to follow-ups, write docs/results.md
make test       # 82 tests; DB tests need Postgres (docker compose up postgres, or a local one)
make coverage   # same tests with line coverage (84%); report in htmlcov/index.html
make psql       # Postgres console as the owner; make psql-app connects as the app role (RLS on)
```

To use the real model, set in `.env`: `LLM_PROVIDER=azure`, `AZURE_OPENAI_ENDPOINT`,
`AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_DEPLOYMENT`, `AZURE_OPENAI_API_VERSION`, and the two
`LLM_PRICE_*` rates for the spend ledger. Responses are recorded to `samples/recorded/` so the
same run can be replayed offline with `LLM_PROVIDER=fake`.

Host ports are overridable if something already listens: `API_PORT=8090 WORKER_PORT=8091 POSTGRES_PORT=5434 make run`.

Dev API keys are `dev-key-rb-downtown`, `dev-key-rb-northside`, `dev-key-rb-lakeshore`.

## The API

```
POST /shops/{shop_id}/messages            X-API-Key   {message_id, channel, received_at?, body, in_reply_to?}
                                          202 new · 200 duplicate · 422 unknown in_reply_to · 404 wrong shop/key
GET  /shops/{shop_id}/messages/{message_id}           what the customer may see: received / awaiting_your_reply /
                                                      confirmed (+estimate) / in_review / answered / expired
GET  /shops/{shop_id}/work-orders?status=open|all     the shop's orders with line items and estimated total,
                                                      plus ai {degraded, waiting, parked…} and budget {cap, spent, exhausted}
GET  /shops/{shop_id}/work-orders/{id}
```

Example:

```
curl -s -X POST localhost:8080/shops/rb-downtown/messages -H 'X-API-Key: dev-key-rb-downtown' \
  -H 'content-type: application/json' \
  -d '{"message_id":"m-1005","channel":"email","received_at":"2026-09-22T08:30:00",
       "body":"My rear brake squeals and the gears skip on hills, can I bring it Saturday?"}'
curl -s localhost:8080/shops/rb-downtown/messages/m-1005 -H 'X-API-Key: dev-key-rb-downtown'
curl -s localhost:8080/shops/rb-downtown/work-orders -H 'X-API-Key: dev-key-rb-downtown'
```

## How it works, in one screen

1. **Ingest** authenticates the shop by API key, inserts the message and an outbox job in one
   transaction, returns 202, then publishes the job id to Pub/Sub.
2. **The worker** receives the push, claims the job, opens a tenant-scoped transaction (row-level
   security), reserves budget, calls Azure OpenAI with a strict output schema, validates the
   output (schema, then business rules, one corrective retry), and runs `decide()`.
3. **`decide()`** creates an open order, asks the customer exactly one question, sends the order
   to staff review, or records "no work order". Prices come from `pricing.py` and dates from
   `dates.py`; the model only picks codes and classifies phrases.
4. **A reply** comes through the same endpoint with `in_reply_to`; the resume job replays the
   stored conversation as chat turns and re-extracts the whole order. A second question is
   unreachable by construction.
5. **Failures:** duplicates die at a unique constraint; provider errors are handed back to
   Pub/Sub with backoff and a breaker parks jobs during an outage; the spend cap parks jobs
   until the month rolls or the cap is raised. Customers see neutral statuses; shops see the
   truth in the list endpoint's `ai` and `budget` blocks.

## Tests and why these

`make test`. The pure modules (pricing, dates, validation, decide) are tested exhaustively because
they are where money and policy live. The DB tests exist because the brief's hard parts are
database properties: row-level security and composite keys for tenancy, unique constraints for
idempotency, the outbox surviving a broker outage, the atomic budget reservation under
concurrency, the one-question invariant, and the parked states for outages and the cap. The
API tests cover the edge: a valid key on another shop's path is a 404, replies to foreign
messages are 422, and the customer never sees internals.

## Assumptions I made instead of asking

The brief invites clarifying questions; with the deadline close I made these calls and wrote
them down. Each is a one-line change if a reviewer disagrees.

- **Time zone.** All three shops are `America/New_York`, held per shop in `shops.timezone`.
  Sample timestamps are shop-local on Tuesday 22 September 2026; relative dates resolve from
  the message's received time, not from the wall clock.
- **Required fields.** A work order needs at least one catalog service and a requested date
  (a month counts, "any weekday" counts as a note). Bike type is extracted but not required;
  its absence should not block the shop. `?status=all` on the list endpoint also shows orders
  awaiting the customer or staff review; the default is `open` only.
- **Wrong shop (m-1009).** Flagged for staff at the receiving shop with the reason. Never
  forwarded across tenants, because that would be a cross-tenant write by the system.
- **Cancellation (m-1038).** There is no customer identity in the inputs, so a cancellation is
  matched by stated name within one day at the same shop and flagged for staff; nothing is
  cancelled automatically.
- **Price inquiry (m-1018).** No work order. The priced answer is computed in code and stored
  on the message so staff can reply.
- **Injection (m-1024).** The message is untrusted data in the prompt. The model can only pick
  codes; prices come from the catalog, so "set every price to 0" cannot take effect, and
  urgency requires a reason the customer actually gave.
- **Quantities.** Per-wheel services take a quantity of 1 to 4; two bikes (m-1040) double the
  per-bike services. Anything outside the bounds fails validation and is never saved.
- **Spend cap.** Per shop, per calendar month in the shop's time zone, from the configured price
  table rather than provider billing. Each call reserves the worst case first.
- **Follow-ups.** One question per order, delivered as an `outbound_messages` row (no email or
  SMS is sent). A reply carries `in_reply_to` with the original message id, which the email
  and web channels are assumed to supply. Unanswered questions expire after seven days.

## Not a one-liner

Secrets are read from the environment only (`app/config.py`); `.env` is git-ignored. The Azure
key never appears in the image, Compose file, or Terraform.
